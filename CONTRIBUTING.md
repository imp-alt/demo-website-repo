# Contributing

## Repo layout

```
index.html               the entry page — inline CSS, no build output
assets/js/main.js        the emoji-orbit module (the only script)
.github/workflows/ci.yml checks, plus the Pages deploy on pushes to main
package.json             dev-only tooling; the site itself has no dependencies
package-lock.json        generated by npm — never hand-edit
eslint.config.js         flat ESLint config
.htmlvalidate.json       html-validate config
.prettierrc.json         Prettier config
.prettierignore          paths Prettier should not format
.gitignore               node_modules only
README.md                what the site is and how to run it
CONTRIBUTING.md          this file
CHANGELOG.md             release notes, Keep a Changelog format
AGENTS.md                rules for automated contributors
```

The site lives at the repository root because that is what GitHub Pages serves.
Do not move it into a `docs/` or `src/` directory.

## No frameworks, no build step

This is a hard rule. The files in the repository are the files that get served.
Do not add a framework, a bundler, a transpiler, a CSS preprocessor, a runtime
npm dependency, or a server. Node and npm appear only in CI to run the three
checks. Nothing referenced by `index.html` may point at `node_modules` or at a
generated directory such as `dist/` or `_site/`.

## Setting up

```sh
npm ci
```

`npm ci` installs the pinned dev tooling from `package-lock.json`. If you change
a dependency in `package.json`, regenerate the lockfile with `npm install` and
commit it; never hand-write or edit a lockfile by hand, because CI's `npm ci`
validates it against `package.json`.

## Running the checks locally

Run everything CI runs:

```sh
npm run check
```

Or individually:

```sh
npx prettier --check .
npx html-validate .
npx eslint .
```

To let Prettier fix formatting instead of reporting it:

```sh
npm run format
```

Preview the site over HTTP — `file://` will not run the animation, because an ES
module is CORS-blocked from a `null` origin:

```sh
python3 -m http.server 8000
```

### Fix the code, not the rules

If a check fails, change the offending file. Do not add a rule to a config, do
not add an ignore entry, and do not add an inline disable comment to make CI
green.

The one exception is documented below, and it is a formatting disagreement
between two tools rather than a relaxation of what is being checked.

## Two settings that exist because the tools disagree

Prettier and html-validate have different opinions about HTML syntax style, so
`.htmlvalidate.json` carries exactly two deviations:

- `void-style: off` — Prettier writes void elements as `<meta />`, which
  html-validate's default would otherwise reject.
- `doctype-style: lowercase` — Prettier lowercases the doctype to `<!doctype
html>`, which html-validate's default would otherwise reject.

Both settings only stop the tools arguing about _style_. They do not turn any
check off: an uppercase `<!DOCTYPE html>` still fails, because Prettier rewrites
it and then reports the file as unformatted. Keep both settings, and if a future
formatting conflict appears, prefer reformatting the file to adding a rule.

## Branches, commits and pull requests

- Branch from `main` with a short kebab-case name, e.g. `add-about-page`.
- Open a pull request against `main`; do not push directly to `main`.
- Use [Conventional Commits](https://www.conventionalcommits.org/) for every
  commit message: `feat:`, `fix:`, `docs:`, `chore:`, `ci:`, `refactor:`,
  `test:`, `perf:`. A scope is welcome where it helps, e.g.
  `feat(orbit): slow the spin down`.
- Every PR updates `CHANGELOG.md` with an entry under **Unreleased**. If a PR
  forgets it, add the entry in the PR rather than merging without one.
- CI has to be green before merge.

## Adding a page

1. Create the HTML file at the repository root, e.g. `about.html`, reusing the
   `<style>` block and the `<script type="module" src="assets/js/main.js">` tag
   from `index.html` as the starting point.
2. Link to it from `index.html` so it is reachable.
3. Add it to the collect step in `.github/workflows/ci.yml`, which copies the
   site into `_site` file by file:

   ```yaml
   cp about.html _site/about.html
   ```

   Anything not listed there is not deployed, which is the point: the artifact
   must contain only `index.html`, the other pages, and `assets/`.

4. Run `npm run check` and preview over HTTP before opening the PR.
